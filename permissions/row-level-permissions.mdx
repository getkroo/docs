<Info>
This permissions model takes effect on **October 18, 2026**. Before then, Kroo has only two user types: **Admins** and **Non-Admins**.
</Info>

Both **Database Access** and **Row Level Permissions** are managed using the [Resource Access Pane](/permissions/resources). Databases are where connection data lives once it is brought into Kroo. Databases can be managed in one of three configurations:

1. Kroo-hosted Data Warehouse
2. Client-hosted Data Warehouse
3. Multiple client-hosted Data Warehouses

<Info>
Kroo supports connections to a wide variety of data destination platforms. Currently, only Microsoft SQL and Microsoft Fabric data destinations are compatible with Kroo's Row Level Permissions capabilities.
</Info>

Data brought into the Kroo platform may be sensitive, including financial or performance management data. Managing Database Access at the Resource level controls user and group visibility within the Kroo app. Row Level Permissions then control which database tables and rows a user can see within the database itself. RLP is required for users to view data, even if Data Warehouse access is granted at the Resource level.

To configure RLP, select `Row-level permissions` in the desired database. This opens the Row Level Permissions window:

<Frame>
  <img
    src="/images/permissions/rlp-groups.png"
    alt="Row-Level Permissions window listing groups"
  />
</Frame>

Row Level Permissions are managed in groups. To create a new group, select **+ Create Group**. In the New Group window, enter a `Group name`, add an optional `Description`, and select **Continue to logic**.

In the following window, select which tables to include in the group and define the rules that govern their visibility. To do so, select `+ Add Table`.

<Frame>
  <img
    src="/images/permissions/rlp-new-group.png"
    alt="New group window on the Table and Row Logic step"
  />
</Frame>

Then select the table or tables you would like to grant access to and select `Add table(s)`:

<Frame>
  <img
    src="/images/permissions/rlp-add-tables.png"
    alt="Table Access picker with one table selected"
  />
</Frame>

Expand your selected table or tables by clicking the chevron next to the table name, then select your desired filter type. Options are:

- No filter (full access)
- Conditions
- Raw SQL

Define your preferred filter, if applicable, then select `Save Filter` and `Continue to role access`.

<Frame>
  <img
    src="/images/permissions/rlp-filter.png"
    alt="Conditions filter on a table"
  />
</Frame>

You will then be brought to the Resource Access Pane, where you can set which roles and users should be included in this Row Level Permissions group. RLP can be revised and edited later from the Row Level Permissions window.

## Filter types

<Tabs>
  <Tab title="No filter (full access)">
    Members see **all rows** in this table. Use this when the table doesn't contain sensitive data or when members should have unrestricted access to it.
  </Tab>
  <Tab title="Conditions">
    Build a row filter with the point-and-click condition builder.

    | Field | Description |
    |-------|-------------|
    | **Column** | The column to filter on (e.g., `project_id`, `company`, `region`) |
    | **Operator** | The comparison: `equals`, `not equals`, `contains`, `greater than`, `less than`, etc. |
    | **Value** | The value to match (e.g., `123`, `West`, `Active`) |

    When multiple conditions are added, choose a logic mode:

    - **ALL conditions must match (AND)** — every condition must be true for a row to be visible
    - **ANY condition must match (OR)** — at least one condition must be true

    **Example:** to restrict members to Project ID 123 in the `kroo_procore.projects` table, set Column = `project_id`, Operator = `equals`, Value = `123`.
  </Tab>
  <Tab title="Raw SQL">
    Write a custom SQL `WHERE` clause for advanced filtering — useful when conditions are complex or need to reference other columns dynamically.

    ```sql
    region = 'West' AND status != 'Closed'
    ```
  </Tab>
</Tabs>

<Info>
Use **Preview Table Data** to see the table's columns and sample rows before building your filter.
</Info>

A user can belong to multiple groups — their effective access is the **union** of all their groups. To check a group's filters from a member's point of view, use **Test as User** in Kris AI Context Settings.
